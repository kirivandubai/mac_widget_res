# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Команды

```bash
./build.sh              # сборка в build/ResBar.app
./build.sh --install    # плюс установка в /Applications и перезапуск
./check.sh              # самопроверка: сверка с top, разбор данных, замеры (~10 с)
./preview.sh [папка]    # отрисовка панели в PNG без запуска в строке меню
```

Проверка на предупреждения компилятора (сборочный скрипт их не выделяет):

```bash
swiftc -O -swift-version 5 -target "$(uname -m)-apple-macos14.0" -o /dev/null Sources/*.swift
```

## Как устроена сборка

Никакого Xcode, SwiftPM и manifest-файлов: `build.sh` вызывает `swiftc` из Command Line
Tools по `Sources/*.swift`, кладёт рядом `Resources/Info.plist`, рисует иконку через
`Tools/MakeIcon.swift` и подписывает бандл ad-hoc. **Подпись обязательна** — без неё macOS
не даёт приложению закрепиться в строке меню. Новый файл в `Sources/` подхватывается сам.

Оба инструмента (`Tools/SelfCheck`, `Tools/Preview`) собираются из всех исходников,
**кроме `Sources/main.swift`** — у них своя точка входа. Поэтому код, который должен быть
доступен проверкам, не может жить в `main.swift`.

Приложение живёт в строке меню без поддержки Apple Events, и `osascript -e 'quit app'`
его не закрывает: `build.sh --install` дополнительно делает `pkill`, иначе `open` увидит
запущенный экземпляр и оставит работать старую сборку.

## Тесты

Отдельного тест-раннера нет; всё, что есть, — `Tools/SelfCheck/main.swift`: один
последовательный прогон проверок с выводом галочек и ненулевым кодом возврата при провале.
Фильтра по отдельной проверке нет — чтобы прогнать часть, временно правьте этот файл.

Проверки не декоративные: именно они поймали, что `proc_pid_rusage` на Apple Silicon
отдаёт время в тактах mach, а не в наносекундах. **При исправлении бага сюда добавляется
проверка** — так в наборе появились сверка форматирования на границе ГБ/МБ, проверка того,
что любая надпись помещается в фиксированную ширину значка, и отсев своих процессов из `ps`.

Панель проверяется отрисовкой в PNG (`./preview.sh`) — читайте получившийся файл.
Живую строку меню (положение и цвет надписи, подсветку значка) отрисовать нельзя:
такую проверку нужно просить у пользователя.

## Архитектура

`MetricsStore` (@MainActor, @Observable) — единственный источник данных для интерфейса.
Из него растут два независимых потребителя: `StatusItemController` (надпись у часов)
и `PanelView` (панель). Два контура опроса с разной ценой:

- **Дешёвый, работает всегда:** `CPUSampler` + `MemoryReader` — 2 мкс на цикл, частота
  из настроек.
- **Дорогой, только при открытой панели:** `ProcessSampler` на последовательной очереди
  `processQueue`. Один таймер на оба списка процессов, в ритме выбранной частоты;
  вызов `ps` добавляется каждый N-й тик, чтобы выходило примерно раз в пять секунд.
  Двух таймеров тут быть не должно: когда они были, на общем тике оба снимали свои
  процессы подряд и вторая дельта считалась за десятки миллисекунд вместо секунды.

Вещи, которые не видны из одного файла:

- **Два источника данных о процессах.** Свои процессы ядро отдаёт напрямую
  (`proc_listpids` + `proc_pid_rusage`, ~2 мс), чужие приходится добывать через `/bin/ps`
  (~80 мс). Сводит их `ProcessSampler.combinedProcesses()`; в выводе `ps` свои отсеиваются
  **по uid**, а не по прошлой выборке — иначе состав списка зависел бы от устаревшего снимка.
- **Всё считается дельтами** между двумя выборками по монотонным часам
  (`ProcessInfo.systemUptime`, не `CFAbsoluteTimeGetCurrent`: настенное время скачет от NTP).
  После любой паузы обязателен `reset()` — иначе первая дельта будет посчитана за всё
  время простоя.
- **`ProcessSampler` — `@unchecked Sendable`** и рассчитан строго на одну последовательную
  очередь. С главного потока его звать нельзя. Группировка и отбор топ-5 в `MetricsStore`
  объявлены `nonisolated static` именно для того, чтобы выполняться там же, в фоне.
- **Сон дисплея** останавливает *все* таймеры (`pause()`/`resume()`), а не только основной.
- **Панель — собственное `NSPanel`, а не `NSPopover`:** popover уезжает верхним краем под
  вырез экрана. Положение считают чистые статические `PanelWindowController.size/origin`,
  на них есть проверки. Закрытие идёт единственным путём — через `windowWillClose`.

## Инварианты потребления

Приложение висит в строке меню круглосуточно, и его собственный расход — предмет проекта,
а не мелочь. Раздел README «Сколько потребляет сам» перечисляет решения, которые легко
потерять при доработках, с ценой каждого в замерах; **при изменении этих мест обновляйте
и цифры там**. Коротко, самое неочевидное:

- Надпись у часов рисует `StatusTitleView` через `CATextLayer`. Штатный `attributedTitle`
  перерисовывает кнопку целиком и стоит втрое дороже — это была самая дорогая часть
  приложения, дороже самих замеров в сотни раз.
- Панель создаётся при открытии и освобождается при закрытии; секции панели —
  самостоятельные `View`, иначе обновление списка процессов пересобирает и графики.
- Графики рисуются `Shape`, а не `Canvas` (у контекста `Canvas` собственный буфер, 65 МБ).
- У полос долей нет плавной анимации: четверть секунды покадровой отрисовки на каждое
  обновление стоила почти половину расхода открытой панели.
- Тики процессора берутся сложенными по всем ядрам (`host_statistics`); `host_processor_info`
  ради ненужной разбивки выделяет память в ядре и стоит в 13 раз дороже.

Мерить так: по pid приложения читать `proc_pid_rusage` дважды с интервалом и считать
`ri_user_time + ri_system_time` за период, `ri_phys_footprint` и пробуждения
(`ri_interrupt_wkups + ri_pkg_idle_wkups`). Замерять нужно установленную или собранную
копию, а не гадать по коду: догадки в этом проекте дважды оказывались неверными.

## Соглашения

Проект русскоязычный целиком: интерфейс, комментарии, документация, сообщения коммитов.
Дробные числа выводятся с запятой (`Format.string`), память — в двоичных единицах,
как в Мониторинге системы.

Комментарии объясняют, **почему** сделано так, а не что делает код, и часто содержат цену
решения в замерах или историю ошибки, которая к нему привела. Держите этот стиль: именно
такие комментарии не дают случайно откатить дорогое решение.
